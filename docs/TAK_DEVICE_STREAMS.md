# Device-stream foundation

This is an experimental gateway and browser foundation for presence-authorized routing. It does not enable directed chat or claim native-client interoperability. It is disabled by default. `TAK_DEVICE_STREAMS=1` selects the adapter in the loopback gateway or private HTTPS server, including named principal instances. It requires a fixed verified-TLS TAK upstream and rejects mesh/bridging configurations. With the flag absent, the original single-upstream behavior, 16-browser limit and four-session named-account limit remain intact.

`server/providers/tak/deviceStreams.js` wraps the existing verified-TLS server-link factory. It maintains one shared feed for SA-off devices and one stream per explicitly publishing device UID. The first endpoint-bearing event is that device's authorized self-SA; non-SA endpoint claims are rejected, including after reconnect. No registration control or position is invented. A presence lease lasts at most 30 seconds, refreshed only by valid self-SA. Stop, lost authorization, last-reference removal, expiry and destruction close the corresponding route and cancel unwritten work. Duplicate UID tabs share one stream and a single presence publisher. Reconnect clears the local presence-write indicator and cancels submissions from the previous stream generation; only a fresh authorized self-SA can set that indicator again.

The opt-in WebSocket control `{ "op": "presence", "enabled": false, "id": "request_1" }` stops only the calling tab's owned presence route. It accepts no target UID. Its acknowledgment contains `op: "presence"`, `enabled: false`, the calling device UID and the same `id`; a refused valid STOP has `op: "reject"`, `command: "presence"`, the same `id` and a reason. IDs use 1–64 ASCII letters, digits, `_` or `-`. The earlier two-key control is also accepted. The browser now sends fresh correlated IDs and accepts only the matching socket, generation, device UID and ID, so a delayed acknowledgment cannot confirm a newer STOP.

After this tab has submitted self-SA through an advertised device-stream gateway, SA-off, cleared position/private state and stopped, hidden or unavailable GPS request route shutdown. New self-SA waits while STOP is pending. The panel distinguishes requested, confirmed, refused and unconfirmed shutdown. A refusal, send failure or 2.5-second acknowledgment timeout closes the browser connection without automatic reconnect. Legacy gateways do not receive the new control. The browser implementation is integrated in the release candidate; combined release validation remains pending. Confirmed STOP describes the gateway's owned route, not remote peer state. A submitted self-SA is a local socket-write result, not a TAK Server UID-registration acknowledgment. Server policies that bind certificate UID to device UID may require distinct device credentials; no server validation is bypassed here.

Limits include 4 upstreams per pool (including the shared feed), 32 process-wide, 32 identities per pool, 256 pending submissions / 1 MiB per principal and 8 MiB process-wide queued bytes. Process-wide UID claims reject concurrent cross-pool identity reuse. Verified TLS, existing server-link queue expiry/write-buffer limits and actual submission outcome semantics remain authoritative. A submitted write is not peer receipt or confirmed registration.

Opt-in streams share a process-wide dial gate: at most two TLS handshakes run concurrently and at most 32 admitted/queued attempts are retained. Admission is reserved before opening the socket. A separate 15-second handshake deadline releases silent unauthenticated attempts; certificate rejection, failure, successful verification, cancellation and close release exactly once. Canceled queued generations never dial later. Reconnect retains the existing exponential 1–30-second backoff with 0–250 ms added jitter, capped at 30 seconds overall. The legacy link path does not gain a handshake timer, admission queue or jitter. These are connection-resource controls, not confirmation that an official server has registered a UID or finished retiring a replaced subscription.

Every wire has a 200 events/s, 1,000 burst frame cap and 1 MiB/s byte cap. A stable pool-lifetime bucket enforces the chosen principal maximum of **800 wire events/s and 4,000 burst**, plus 4 MiB/s and an 8 MiB byte burst, before recipient deduplication. Replacing streams cannot refill that aggregate allowance. This replaces the earlier proposed 200 principal events/s aggregate. Delivery has a fixed 4 MiB/s principal budget divided fairly among its live device UIDs. It does **not** spend one shared 200 events/s bucket for every copied public feed. Four 100 Hz copies can reach four intended devices without one recipient consuming another's frame budget; a byte flood on one wire cannot consume another device's reserved delivery share. Distinct-feed and rapid stream-replacement tests exhaust bursts, verify the 800-event one-second refill and retain fixed replay/dedup bounds. This bounds accepted parsing/delivery work and retained memory; it is not a target-device CPU/frame-time guarantee.

Ingress carries its actual stream owner through per-device deduplication and contact replay. A missing/stripped `marti` destination never authorizes principal-wide fanout. Device streams feed only that UID's authorized tabs; the shared feed reaches SA-off devices only. Replay and dedup maps are partitioned under fixed aggregate bounds and rebalanced immediately when identities attach. Private chat is not contact replay, and retired-stream callbacks cannot reach a new owner. The gateway adapter retains event authorization, broadcast-only chat policy, authenticated-session checks, bounded WebSocket buffers and existing public local-event fanout. Directed chat remains rejected in both directions. Private ingress never enters the principal-wide router/replay map. The opt-in adapter divides the original principal replay budget conservatively: 1,000 entries / 4 MiB for public browser-origin objects and 1,000 entries / 4 MiB shared across all pool replay partitions. The total remains 2,000 entries / 8 MiB. The standalone pool's default budget is 2,000 entries / 8 MiB. Status exposes only the requesting WebSocket's presence record, plus aggregate stream and replay counters; public HTTP status retains its existing limited summary.

Focused tests in `src/tooling/takDeviceStreams.test.mjs` cover lazy SA-off operation, real USER-SA construction, exact identity/endpoint/freshness, duplicate-tab ownership, expiry/stop, 4 per principal and 32 per process limits, cross-pool UID conflict/release, stripped-routing isolation/replay, copied-feed fairness, byte flooding, aggregate queued work, cancellation/reconnect epochs, late outcomes and receive-only behavior. `src/tooling/takDeviceGateway.test.mjs` adds actual loopback HTTP/WebSocket sessions with injected uplinks for default-off capacities, opt-in configuration, exact recipient delivery/replay, scoped status, stop ownership, endpoint denial and observer/directed-chat policy. `src/tooling/takDialAdmission.test.mjs` adds bounded admission/deadline/cancellation/generation tests and actual local silent-peer and mTLS verification/release tests, including observed socket-close completion and no queued CoT leakage to rejected-server connections. Browser STOP has client/transport tests for correlation, timeout and re-enable behavior; the combined candidate still requires validation. These do not prove official TAK Server interoperability of this new pool. That acceptance, rapid same-UID route replacement and native-device directed-chat acceptance remain subsequent gates.

The focused Node24 run passed 86 tests across the pool, WebSocket adapter and dial-admission files plus the existing gateway, TLS-security and named-operator tests. Import-direction and package-boundary checks also passed. Existing genuine local mTLS tests remain green; pool routing tests use injected transport factories, and dial admission uses both injected sockets and genuine local TLS peers. This result does not substitute for actual pool/official-server acceptance.

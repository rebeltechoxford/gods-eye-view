# Device-stream foundation

This is an experimental server-only foundation for presence-authorized routing. It does not enable directed chat or claim native-client interoperability. It is disabled by default. `TAK_DEVICE_STREAMS=1` selects the adapter in the loopback gateway or private HTTPS server, including named principal instances. It requires a fixed verified-TLS TAK upstream and rejects mesh/bridging configurations. With the flag absent, the original single-upstream behavior, 16-browser limit and four-session named-account limit remain intact.

`server/providers/tak/deviceStreams.js` wraps the existing verified-TLS server-link factory. It maintains one shared feed for SA-off devices and one stream per explicitly publishing device UID. The first endpoint-bearing event is that device's authorized self-SA; non-SA endpoint claims are rejected, including after reconnect. No registration control or position is invented. A presence lease lasts at most 30 seconds, refreshed only by valid self-SA. Stop, lost authorization, last-reference removal, expiry and destruction close the corresponding route and cancel unwritten work. Duplicate UID tabs share one stream and a single presence publisher. Reconnect clears the local presence-write indicator and cancels submissions from the previous stream generation; only a fresh authorized self-SA can set that indicator again.

The opt-in WebSocket control `{ "op": "presence", "enabled": false, "id": "request_1" }` stops only the calling tab's owned presence route. It accepts no target UID. Its acknowledgment contains `op: "presence"`, `enabled: false`, the calling device UID and the same `id`; a refused valid STOP has `op: "reject"`, `command: "presence"`, the same `id` and a reason. IDs use 1–64 ASCII letters, digits, `_` or `-`. The earlier two-key control is also accepted, but browser integration must use fresh IDs to distinguish delayed acknowledgments after re-enabling presence. The current browser UI has not yet been wired to this new control; its existing SA-off action stops new beacons, and this experimental server route then expires within the lease bound. Do not describe this as an immediate browser stop until that integration is accepted. A submitted self-SA is a local socket-write result, not a TAK Server UID-registration acknowledgment. Server policies that bind certificate UID to device UID may require distinct device credentials; no server validation is bypassed here.

Limits include 4 upstreams per pool (including the shared feed), 32 process-wide, 32 identities per pool, 256 pending submissions / 1 MiB per principal and 8 MiB process-wide queued bytes. Process-wide UID claims reject concurrent cross-pool identity reuse. Verified TLS, existing server-link queue expiry/write-buffer limits and actual submission outcome semantics remain authoritative. A submitted write is not peer receipt or confirmed registration.

Every wire has a 200 events/s, 1,000 burst frame cap and 1 MiB/s byte cap. With four streams the chosen principal maximum is **800 wire events/s and 4,000 burst**, before recipient deduplication, rather than the earlier proposed 200 principal events/s aggregate. Delivery has a fixed 4 MiB/s principal budget divided fairly among its live device UIDs. It does **not** spend one shared 200 events/s bucket for every copied public feed. Four 100 Hz copies can reach four intended devices without one recipient consuming another's frame budget; a byte flood on one wire cannot consume another device's reserved delivery share. Distinct-feed tests also exhaust all four independent bursts and verify the 800-event one-second refill and fixed replay/dedup bounds. This bounds accepted parsing/delivery work and retained memory; it is not a target-device CPU/frame-time guarantee.

Ingress carries its actual stream owner through per-device deduplication and contact replay. A missing/stripped `marti` destination never authorizes principal-wide fanout. Device streams feed only that UID's authorized tabs; the shared feed reaches SA-off devices only. Replay and dedup maps are partitioned under fixed aggregate bounds and rebalanced immediately when identities attach. Private chat is not contact replay, and retired-stream callbacks cannot reach a new owner. The gateway adapter retains event authorization, broadcast-only chat policy, authenticated-session checks, bounded WebSocket buffers and existing public local-event fanout. Directed chat remains rejected in both directions. Private ingress never enters the principal-wide router/replay map. The opt-in adapter divides the original principal replay budget conservatively: 1,000 entries / 4 MiB for public browser-origin objects and 1,000 entries / 4 MiB shared across all pool replay partitions. The total remains 2,000 entries / 8 MiB. The standalone pool's default budget is 2,000 entries / 8 MiB. Status exposes only the requesting WebSocket's presence record, plus aggregate stream and replay counters; public HTTP status retains its existing limited summary.

Focused tests in `src/tooling/takDeviceStreams.test.mjs` cover lazy SA-off operation, real USER-SA construction, exact identity/endpoint/freshness, duplicate-tab ownership, expiry/stop, 4 per principal and 32 per process limits, cross-pool UID conflict/release, stripped-routing isolation/replay, copied-feed fairness, byte flooding, aggregate queued work, cancellation/reconnect epochs, late outcomes and receive-only behavior. `src/tooling/takDeviceGateway.test.mjs` adds actual loopback HTTP/WebSocket sessions with injected uplinks for default-off capacities, opt-in configuration, exact recipient delivery/replay, scoped status, stop ownership, endpoint denial and observer/directed-chat policy. These do not prove real TLS/server interoperability of this new pool. That acceptance, browser SA-stop integration, a global handshake scheduler and native-device directed-chat acceptance remain subsequent gates.

The focused Node24 run passed 74 tests across these two files plus the existing gateway, TLS-security and named-operator tests. Import-direction and package-boundary checks also passed. Existing genuine local mTLS tests remain green; the new pool-specific transport factories are injected in these tests, so this result does not substitute for actual pool/server acceptance.

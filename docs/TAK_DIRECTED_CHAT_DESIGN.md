# Directed GeoChat: scoped implementation and acceptance plan

Design only, based on the real official-server experiments in [TAK_REAL_SERVER_ACCEPTANCE.md](TAK_REAL_SERVER_ACCEPTANCE.md). No production change, server launch, native-client acceptance or new download is implied by this document.

## Decision and evidence

Use **one bounded upstream TLS connection per active device UID**, scoped under its existing authenticated principal, for the first directed-chat implementation. Require an **explicitly authorized self-presence report with a real measured or deliberately operator-set position** before offering directed chat. Keep SA-off broadcast/marker workflows working. Do not send endpoint-bearing fake-position control events to obtain a route.

The tested official server registers only the first endpoint-bearing UID per TLS stream. Two browser identities sharing a gateway stream can broadcast markers without SA, but neither gets a directed return route until registered; after experimental registration only the first UID is reachable. Separate TLS streams work independently. The experimental `t-x-c-t` registration is also replayed to late joiners through the server's latest-SA cache. It is rejected as a production registration method.

This design targets one-to-one GeoChat through the configured TAK Server. Group chat, arbitrary rooms, UDP/direct-to-peer networking, mission chat, receipts and store-and-forward guarantees remain separate slices. No client-provided host, port, certificate, destination group or raw routing extension is accepted.

## Position-free registration audit

The audit checked the official public protocol text and the exact tested Server source, commit `5187abd46d827d37cfc5708805eced197a837e49` / `5.7-RELEASE-14`. **No documented position-free API that binds a new UID to an existing authenticated streaming connection has been established.** This is a scoped finding, not a claim that no future release or supported plugin can provide one.

## Supported first presence path

Reuse `client.setFix`, `setSaEnabled`, `buildSelfSa` and the existing explicit GPS/map-center controls. A valid field-navigation coordinate may also be offered through a separate **Use as operator-set presence** action; focusing a waypoint or creating a marker must never enable SA or change self position implicitly.

- GPS presence requires an available measured fix, existing freshness/visibility/watch checks, and explicit SA consent. No emulator/default coordinate is represented as measured GPS. The gateway validates a reported fix and identity; it cannot attest that a browser-supplied GPS claim came from hardware.
- Operator-set presence remains labeled `USER` / `h-e`, with the position and its observation age visible. The user must deliberately set/confirm it and enable sharing. Retain unknown altitude/accuracy as unknown.
- The gateway allocates the device stream only after authenticated identity and a valid explicit presence intent. Its **first endpoint-bearing write must be that identity's authorized self-SA**, ahead of queued chat. Imported contacts, markers, chat and keepalives must never claim a stream's registration identity.
- Add explicit presence-stop signaling. SA off, GPS stopped/unavailable, hidden/stale GPS, session expiry, logout and destruction cancel queued presence/direct messages and remove that device's routed stream. A missed update expires the presence lease after `30 s` (three current `10 s` beacon intervals); no stale fix is refreshed on the browser's behalf.
- A USER position can remain deliberately static while that live session continues publishing SA. Its original observation age must not be rewritten to pretend a new measurement occurred.
- Stopping presence cannot retract data already received by peers. Do not promise instant removal of previously shared positions or server history; stop future publication and let documented stale/disconnect behavior apply.

The official stream has no established registration ACK. A local socket write or ping reply is **not** proof that UID mapping or peer delivery completed. Report `presence sent / return route unconfirmed`, preserve current submission semantics, and test first-message/reply races against the real server. Never add an arbitrary sleep and label it registration confirmation. Native acceptance is required before claiming a reliable directed conversation.

## Pool ownership and bounded resources

Keep current principal isolation: each principal owns its fixed server address, CA and unique credential; its generation changes on credential/role/token rotation. Device pool key: **principal generation + device UID**. Keys and privileged TLS material stay server-side.

| Concern                     | Proposed first behavior                                                                                                                                                                                                                                                                                                                                             |
| --------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Limits                      | At most `4` upstream connections per principal, including any shared SA-off feed; at most `32` process-wide across the current maximum `8` principals. Reserve before dialing; reject excess presence requests explicitly without losing existing broadcast access. Do not multiply an extra permanent base stream onto four device streams.                        |
| Lazy allocation             | Keep one shared stream for SA-off/broadcast-only users when needed. Active presence devices consume their own streams; stop consuming the shared feed for those devices. Retire an unused shared stream before admitting a fourth presence device. Never evict an active user silently.                                                                             |
| Duplicate UID tabs          | Reference-count one pool entry, not one upstream per tab. Only the same principal/generation and compatible identity can join. A single server-enforced presence lease chooses the SA publisher; duplicate tabs can share their conversation view without sending competing beacons. A new owner must explicitly retain/enable presence after the old owner leaves. |
| UID ownership               | Maintain a bounded process-wide active UID claim registry. Reject another principal claiming an active UID, even if group isolation hides its contacts. Return a generic conflict without exposing the other principal. Keep UUID namespace/foreign-contact collision checks. Do not authorize by callsign.                                                         |
| Reconnect                   | Retain `serverLink` CA/hostname verification, bounded backoff and queue expiry. Add bounded jitter and at most `2` concurrent process-wide TLS handshakes. A reconnect loses registration state; require a fresh authorized SA before directed work resumes. No replay of an old fix, last message or imported contact to re-register.                              |
| Queues                      | Keep existing per-link caps as ceilings, plus aggregate `256` queued submissions / `1 MiB` per principal and `8 MiB` process-wide queued payload. Preserve `64 KiB` inbound browser frame, `256 KiB` per-link write-buffer and `512 KiB` browser-buffer limits. Ownership cancellation must reach the exact pool entry.                                             |
| Rates                       | Keep per-browser limits and impose an aggregate principal ingress budget across its device streams; increasing stream count must not multiply existing `200 events/s`, `1000` burst upstream ingress authority. Apply fair bounded scheduling so one device cannot starve the rest.                                                                                 |
| Last reference / revocation | Close immediately when the last authorized browser leaves or its presence lease ends; cancel its unwritten work. Expiry/logout/reload/role change destroys affected entries and invalidates callbacks by generation/epoch. No idle upstream may preserve an unowned device route.                                                                                   |
| Observer role               | Preserve receive-only authorization. Observers use the shared group feed and may not publish presence or originate chat/receipts. UID-addressed personal conversations remain unavailable in this first slice; do not synthesize presence just to make them reachable.                                                                                              |

Certificate reuse **within** a principal worked in the isolated lab. It does not prove all operational server policies allow multiple device UIDs or simultaneous streams under one certificate. Check configured UID/certificate binding and connection policy. If the server requires a certificate-bound device UID, provision server-side per-device credentials or constrain that principal to one compatible UID; never turn off the server's validation to make the pool work. Credentials must remain distinct between principals.

## Routing and privacy: retain the device context

Current `createTakGateway` creates one server uplink, one principal-wide router/replay cache and browser fanout. `createServerLink` already provides verified TLS, framing, bounded queues, cancellation and reconnect callbacks, but returns fixed link ID `server`. `router` deduplicates canonical XML globally before fanout. These interfaces need a small pool adapter and explicit ingress context; simply adding four links to the existing broadcast router is unsafe.

The official [stream rewrite filter](https://github.com/TAK-Product-Center/Server/blob/5187abd46d827d37cfc5708805eced197a837e49/src/takserver-core/src/main/java/com/bbn/cot/filter/StreamingEndpointRewriteFilter.java#L172) removes `<marti><dest>` when processing server routing. Incoming XML alone may no longer reveal its original routing constraint. Therefore:

1. Keep the receiving stream's owning UID as trusted transport context, outside browser-supplied CoT. Incoming device-stream events initially go only to that device's authorized tabs. Do not infer broadcast permission from absence of `marti` or an apparently public chatroom label.
2. The shared SA-off stream feeds only SA-off/broadcast-only devices. Presence devices receive their feed through their own streams. Broadcasts still reach each device once through its eligible feed; no principal-wide cross-stream fallback for private messages.
3. Deduplicate and replay **per recipient device** before delivery. A principal-wide first-seen cache must not suppress a second legitimate recipient or let the first copy fan out to other UIDs. Bound per-device caches within a fixed aggregate principal byte budget; keep private chat out of public/contact replay and persistence.
4. Each outbound event selects exactly one owner stream, or the shared feed for existing SA-off public actions. Never fan one submission to every upstream. Server-origin data must not be bridged between those streams or into multicast. Existing local public marker/drawing fanout can remain explicit and deduplicate its eventual echo per device.
5. A same-UID tab is an explicitly shared device conversation; a different UID, principal or credential generation is not. Account switch, logout and privacy reset clear private drafts, conversations, receipts, replay and queued delivery state before another view can receive them.

For a first one-to-one message, prefer a structured intent (`submissionId`, selected `recipientUid`, text) that the gateway validates and canonically builds. Do not generally allow browser-provided `marti` extras. Reuse the selected contact's UID, not its callsign/address. Validate sender ownership, one recipient, participant list, source/to fields, message ID, byte limits, freshness and current permission; reject unknown/group/ambiguous destinations. Maintain a bounded eligible-recipient set learned from supported, fresh contacts on this principal generation's authenticated upstream; imported/local-only entries do not grant remote messaging permission. Expire entries on staleness, removal and credential generation changes. TAK Server remains authoritative for remote group reachability. The gateway must not let a browser name a hidden/off-scope peer merely because it knows a UID; visible contact labels are not cryptographic proof of a person's identity.

Add a typed directed-chat builder/parser and recipient policy without loosening the existing broadcast validator. On inbound native messages, require recipient fields consistent with the transport-owned UID; quarantine unsupported variants rather than broadening them into broadcast. Confirm the accepted native wire variations with genuine client capture before publishing compatibility claims. Hand-authored fixtures may describe the format; do not copy GPL Android application implementation into GEV.

## Smallest safe sequence and acceptance gates

1. **Presence contract and pool seam, no directed UI.** Add bounded `deviceStreams` ownership/leases and unique link metadata around `createServerLink`. Make presence stop/freshness explicit; preserve current broadcast paths when disabled/unavailable. Unit-test lease/refcount/limits/generations/cancel/reconnect with injected clocks and connection factories. Test duplicate tabs, conflicting callsigns, cross-principal UID claims, stale GPS and USER labeling. No replacement gateway or globe rewrite.
2. **Transport isolation and dedup before private content.** Route owned ingress/replay per device and select exactly one outbound link. Real TLS tests exercise two UIDs, same-UID tabs, aggregate caps, out-of-order callbacks, revocation, backpressure and expiry. Duplicate broadcast copies must yield one update per intended device; identical directed payloads to two device streams must reach both separately and no third view. Include a private message whose server strips `marti` and whose remaining XML resembles broadcast.
3. **Real-server authorized presence proof.** In the confined official lab, two explicit synthetic USER positions (clearly labeled test data) register two device streams. Prove replies to each UID, first-message/reply ordering, reconnect with fresh presence, SA-off route withdrawal, last-tab closure, certificate failure and blue/red rejection. Observe late-join replay: real authorized self-SA is expected; no fabricated registration control may appear. Test server connection/UID-validation policy rather than assuming the lab default generalizes.
4. **One-to-one GeoChat and minimal conversation UI.** Add a separate directed builder, strict gateway intent/recipient validation, bounded ephemeral conversations and mobile `44 px` controls. Keep broadcast separate, preserve privacy guards, and clear on authentication changes. Browser acceptance uses actual selections/typing/touch and checks exact intended views, SA-off explanation, limits, cancellation, logout and no leaked drafts/history. Label socket-write success as peer receipt unconfirmed.
5. **Genuine native client gate before interoperability claim.** Use an authorized isolated ATAK/WinTAK/iTAK environment; do not open an operational profile. Exchange messages both directions with two web device UIDs, test native sender/recipient labels and replies, stale/moving/USER positions, reconnect/SA off, duplicate tabs, another principal and a denied group. Record actual versions, captures and supported scope. This remains open until that environment exists and passes.
6. **Receipts and store-forward later.** Do not automatically acknowledge or mark read. Add delivery/read receipts only after their native wire semantics, recipient authorization, message-ID correlation, replay/dedup, explicit read action and failure cases are independently verified. A TLS write, server queue or echoed message is not a receipt. No retry after an ambiguous successful write without an explicit idempotency/peer protocol guarantee.

Completion requires preservation gates as well as the new checks: all existing GEV layers/camera/voice/HUD behavior, TAK parser/store/gateway security tests, current private/account/offline browser gates, formatting/boundaries/build and focused native evidence. Until then, the shipped capability remains the documented broadcast chat implementation; SA-off personal directed delivery and native acceptance must remain plainly unavailable/unverified.
